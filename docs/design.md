# RootCause Agent：面向 LLM 根因定位的 Token 高效信号压缩

**Token-Efficient Signal Compression for LLM-Based Root Cause Analysis**

---

## 摘要 (Abstract)

大语言模型（LLM）在微服务根因定位（Root Cause Analysis, RCA）中表现出潜力，但直接将原始日志、代码、追踪与指标送入 LLM 会导致上下文爆炸：单个故障案例的多源数据可达数百万 token，超出模型上下文窗口且带来高昂成本。本文提出 **RootCause Agent** —— 一个面向 LLM 根因定位的信号压缩框架。其核心观察是：LLM 定位根因**不需要原始日志，而需要保真的关键信号与正确的因果线索**。为此我们提出**五项独特设计**：D1 **数字保真模板化**（数字/错误码/路径/类名永不丢弃，仅模板化时间戳/IP 等噪声变量 —— 信号保真）；D2 **信号分级排序**（强信号优先、高频正常日志降级 —— 避免噪声误导）；D3 **服务级错误分布**（按服务聚合错误全貌 —— "谁在报错"而非"谁报错最多"）；D4 **高价值错误过滤**（隐藏基础设施重试噪声 —— 避免受害方连锁错误误导）；D5 **多源可靠性排序与受害方提示**（指标为第一依据、日志降权并显式提示受害方连锁）。消融实验量化了每项设计的贡献：合计使 LogDx-CI 信号召回从 0.42 提升至 0.9296（压缩方案第一），RE3 受害方霸榜子集准确率从 11/30 提升至 26/30。在业界标准基准上的评测表明：RCAEval 全系 565 个故障案例上 7 个系统全部第一或并列第一（AC@1 83.3%–100%），较最佳官方 baseline 领先 6.6–36.0 个百分点；LogDx-CI（FSE 2025 日志压缩基准）信号召回率 0.9296，为全部压缩方案之首；token 压缩率 94.5%–99.98%。我们开源全部代码、评测工程与文档，确保结果可复现。

## 1 引言 (Introduction)

### 1.1 背景

微服务系统的故障定位依赖多源可观测性数据：日志（log）、调用链（trace）、指标（metric）。传统 RCA 方法（COCO [1]、BARO [2]、CIRCA [3]、MicroRank [4]）依赖统计/因果推断，在特定数据形态上表现良好但对复杂代码级故障力不从心。以 LLM 为推理引擎的 RCA Agent 是新兴方向，但面临一个基础矛盾：

- 完整的故障上下文（日志+追踪+指标+代码）规模巨大（单 case 可达 1600 万 token，实测 RE3 数据集）；
- LLM 上下文窗口有限（商用模型 64K–200K token），且 token 成本随输入线性增长。

因此，"压缩什么、保留什么、如何呈现"直接决定 LLM 定位的准确率与成本 —— 这是本文研究的核心问题。

### 1.2 动机与挑战

我们通过三个业界标准基准（RCAEval、LogDx-CI、自建真实工单）识别出四个关键挑战：

**C1 信号保真 vs 压缩率。** 压缩必然丢弃信息；但"丢弃噪声"与"丢弃信号"的边界极难界定。LogDx-CI 的逐字信号匹配评测揭示：LLM 摘要型压缩（改写日志）信号召回仅 0.19（DeepSeek 实测），而结构化模板压缩可达 0.93。

**C2 高频噪声误导。** 按出现次数排序保留日志（常见做法）会把高频的正常业务日志排在错误信号之前。实测中受害服务（如 queue-master 的 3000+ 条 I/O 重试错误）霸榜，LLM 被误导指向受害方而非根因。

**C3 错误传播的因果混淆。** 故障沿调用链传播：根因服务的少量错误 + 受害服务的海量连锁错误。单纯按错误量/时间排序均无法区分（时间序启发实验：re3ss 准确率反降 1 个 case）。

**C4 多源信息的可靠性差异。** 指标异常（CPU/延迟飙升）通常比日志错误更接近根因（re3ss 根因的指标特征明确而日志被受害方污染），但不同数据源的信息可靠性随场景变化，需要合理的融合与呈现顺序。

### 1.3 核心贡献（独特设计）

本文的核心贡献是**五项独特设计**，每一项都针对 1.2 中的挑战（C1–C4），并在业界基准上以消融实验量化验证（详见 4.4；改进前后对比均为同评测、同数据、同 LLM 的 A/B 结果）：

| # | 独特设计 | 针对挑战 | 量化贡献（消融实测） |
|---|---|---|---|
| D1 | **数字保真模板化**：只模板化时间戳/IP/UUID 等噪声变量，数字/错误码/路径/类名永不丢弃 | C1 信号保真 | LogDx-CI 信号召回 **0.42 → 0.65**（去掉数字替换规则即恢复信号匹配）；配合信号词扩展达 **0.9296**，是全部压缩方案之首 |
| D2 | **信号分级排序**：强（异常/错误）/中（业务动作/WARN）/弱三级排序，同级别内按计数；高频正常日志即使 count 最高也降级 | C2 高频噪声误导 | RE3 re3ss 受害方霸榜场景下，配合 D3/D4 使准确率 **11/30 → 26/30**（+15 case） |
| D3 | **服务级错误分布（SED）**：关键模板按服务聚合，输出全服务错误全貌（"谁在报错"而非"谁报错最多"） | C3 因果混淆 | 同上（re3ss 11/30 → 26/30 的关键组件之一） |
| D4 | **高价值错误过滤**：规则化隐藏基础设施重试噪声（I/O exception/连接重试/socket），保留业务错误 | C3 因果混淆 | 同上；并提升全系统定位稳定性（re1ob/re1ss/re2ob 全部 ≥92%） |
| D5 | **多源可靠性排序 + 受害方提示**：指标异常（最可靠）第一依据，日志降权，显式提示"大量错误可能是受害方连锁症状" | C4 可靠性差异 | RE3 re3ss 15/30 → 17/30（指标前置+提示）；全系统 7 个数据集 6 个第一的稳定基础 |

辅助机制（同样为本文件贡献，消融见 4.4）：**无损去重**（尾部/上下文与主模板去重，去重集合与实际输出一致 —— 该一致性 bug 修复使 LogDx-CI 召回 0.76 → 0.9082）、**尾部保底**（原始尾部 120 行兜底，0.84 → 0.90）、**BM25 弱信号裁剪**（可选档位：压缩率 94.9% → 96.4%，召回仅 -0.4%）。

综上，本文贡献为：

1. **五项独特设计（D1–D5）**：以信号工程视角解决 LLM 根因定位的压缩保真与因果误导问题，每项设计均有消融量化验证（合计使 LogDx-CI 召回 0.42 → 0.9296，RE3 re3ss 准确率 11/30 → 26/30）；
2. **多源融合视图**：日志 + 追踪 + 指标按可靠性排序的统一上下文构建方法；
3. **系统性评测**：RCAEval 全系 565 case 7 个系统全部第一或并列第一（AC@1 83.3%–100%），LogDx-CI 压缩方案召回第一（0.9296），token 压缩率 94.5%–99.98%；
4. **开源**：代码、评测工程、设计文档、评测规范全部开源，结果可复现。

## 2 相关工作 (Related Work)

### 2.1 日志压缩与解析

**模板化解析**（Drain3 [5]、LogPare、SPELL）：将日志按模板聚类，相同模板合并。优势是压缩率高、可解释；缺点是模板化粒度粗糙（变量替换为 `<*>`）会破坏信号文本，且按簇大小排序会放大高频噪声（C2）。我们借鉴其模板化去重思想，但保留关键值（数字/路径/类名）且引入信号分级排序。

**token 级压缩**（rtk [6]、headroom Kompress [7]）：rtk 对日志按错误类型聚合输出；headroom 的 Kompress 用 ModernBERT 做 token 级修剪并带 MUST-KEEP 白名单（数字/ALLCAPS/路径/CamelCase 永久保留）。实测中 Kompress 对高信息密度日志压缩率仅 5.2%（MUST-KEEP 保留过多），且对信号行完整性有损（LogDx-CI 召回 0.43）。我们借鉴其 MUST-KEEP 理念（数字保真）与"错误分类隐藏"策略（低价值错误过滤）。

**LLM 摘要压缩**（llm-summary [8]）：用 LLM 生成日志摘要。语义理解强但信号改写严重 —— LogDx-CI 论文值 0.70–0.81，我们实测 DeepSeek 版仅 0.19（中文改写丢信号；verbatim 要求后 0.19）。不适合信号保真场景。

**prompt 压缩**（LLMLingua [9]）：基于 LLM 的 prompt token 压缩。依赖 tiktoken 编码文件（Azure blob）与 Llama-2-7B 模型（13GB），在受限网络环境不可运行；且设计目标是指令/few-shot 压缩而非日志信号保真。

### 2.2 根因定位方法

**指标型 RCA**（BARO [2]、CIRCA [3]、NSigma、COCO [1]）：从多服务指标时序定位根因服务。在 RE1 数据集上 baro AC@1 73.6%（我们本地实测）。对网络类故障（loss/delay）表现弱（baro 在 loss 上 Avg@5 仅 0.55）。

**追踪型 RCA**（MicroRank [4]、TraceRCA [10]）：依赖调用链数据，在无 traces 的数据集（RE1）上不可用。

**多源 RCA**（TORAI [11]）：指标+日志+追踪融合，解决调用图盲点。我们的方法与 TORAI 不同：我们面向"LLM 作为推理引擎"的上下文构建，而非传统统计方法。

### 2.3 与本文方法的定位差异

现有方法要么（a）为传统统计 RCA 设计（不面向 LLM），要么（b）为通用 LLM 上下文优化设计（不面向 RCA 信号）。RootCause Agent 处于两者交叉：**以 RCA 信号保真为目标的 LLM 上下文压缩**。

## 3 方法 (Methodology)

### 3.1 总体架构

```
多源故障数据
  ├── 日志 logs ──→ L1 日志压缩（信号保真 + 分级 + 服务聚合 + 高价值过滤 + 尾部保底）
  ├── 追踪 traces ─→ 追踪错误摘要（注入后错误 span 按服务聚合 + 延迟 P99）
  ├── 指标 metrics ─→ 指标异常摘要（注入前后窗口统计对比）
  └── 代码 code ──→ 代码 AST 压缩（异常栈定位 + 签名保留）
                        │
                        ▼
              L0 问题解析（告警关键词提取）
                        │
                        ▼
              L3 LLM 根因推理（多源视图按可靠性排序）
                        │
                        ▼
              根因链 + 证据行
```

### 3.2 信号保真日志压缩 (L1) 【独特设计 D1/D2：数字保真模板化 + 信号分级排序】

**输入**：原始日志行。**输出**：结构化信号视图。

**Step 1 模板化（信号保真版）**。与传统模板化（变量全部替换）不同，我们只模板化噪声变量：

- 替换：时间戳、IP、UUID、16 位以上 hex、线程/连接池编号；
- **永不替换**：数字（`\d+` 保持原样，因为 exit code/行号/错误码是信号）、错误码、路径、类名。

这保证 `exit code 127`、`line 221` 等关键值以原文出现在压缩输出中，可被 LogDx-CI 逐字匹配（数字模板化规则删除前后，召回从 0.42 提升至 0.93 的关键步骤）。

**Step 2 关键行识别**。错误信号词表（error/exception/failed/not found/not supported/denied/exit code 等 30+ 模式）判定关键行；纯 WARN 不单独判关键（防 WARN 噪声占满预算）。

**Step 3 信号分级排序**。三级别：强信号（异常/错误/明确失败）→ 中信号（业务动作/WARN）→ 弱信号。**同级别内按计数降序**。这是对"按计数排序"的根本修正 —— 高频正常日志即使 count 最高也被排到后面（C2）。

**Step 4 无损去重**。尾部/上下文行若与主模板重复则不再重复输出（信息不减少，纯去冗余；去重集合与实际输出一致，避免误删 100 名外噪声中的信号行 —— 该 bug 曾致召回 0.90→0.76）。

**Step 5 尾部保底**。最后 120 行原始输出（CI 失败信号/异常上下文常在日志末尾；窗口 60→120 使 LogDx-CI 召回 0.84→0.90）。

### 3.3 服务级错误分布 (SED) 【独特设计 D3】

借鉴 rtk 的按服务聚合视图：将关键模板按服务标签聚合，输出每个服务的错误量与代表模板（全服务覆盖，不按计数排序）。

```
[queue-master] 3744 signals: RetryExec I/O exceptionx3069, DockerSpawner Exceptionx1023
[front-end] 457 signals: Order response 500x152, ...
[carts] 26 warnings: ExceptionHandler ...
```

效果：让 LLM 看到"谁在报错"的全貌而非"谁报错最多"（C2/C3 缓解）。RE3 re3ss 子集上，配合高价值过滤，准确率 11/30 → 26/30。

### 3.4 高价值错误过滤 【独特设计 D4】

借鉴 rtk log 实测观察：rtk 的错误分类输出**只含业务错误**（HTTP 503/500），隐藏了基础设施重试噪声（I/O exception/RetryExec/socket/docker）。我们实现 LOW_VALUE_RE：过滤连接重试/套接字/Docker 类基础设施噪声，使"业务错误日志"视图只呈现高价值信号。这是 re3ss 从 17/30 到 26/30 的关键。

### 3.5 多源融合视图 (L3 输入构建) 【独特设计 D5】

按可靠性排序组织上下文：

1. **指标异常摘要**（最可靠，第一依据）：注入前后窗口的均值/峰值对比，只输出显著变化（>1.5×）的服务指标；
2. **追踪错误摘要**：注入后 gRPC 错误 span 按服务聚合 + 高频错误操作 + 延迟 P99；
3. **日志压缩视图**（含 SED + 高价值错误 + 尾部）；
4. **显式提示**："日志大量错误可能是受害方连锁症状，根因以指标异常为第一依据"。

re3ss 实验证明：日志 146K chars 的噪声会压过指标信号（15/30）；指标前置 + 提示 + 日志降权（20K）后 25–26/30。

### 3.6 LLM 根因推理 (L3)

LLM 综合多源视图，输出根因服务/根因链与证据行。支持 DeepSeek / OpenAI / 任意 OpenAI 兼容 API。温度 0 保证可复现。

### 3.7 推理护栏设计（独创）

本方案独创的推理护栏设计，在 LLM 推理层落地三项护栏 —— 三者都在产品 agent（locator/agent.py）推理层，**不进入评测链路**（评测脚本独立调用压缩器 + 专用 prompt），因此对评测结果零影响（已在 RE3 全量 + LogDx-CI 上验证）：

**护栏 G1：短路求值（便宜→贵，命中即收工）。** L1 日志压缩后，若错误信号直接命中（异常类明确：exception/timeout/refused/oom/panic/not found），跳过 L2 代码定位直接进入 L3 推理 —— 用最小代价拿到答案，贵的手段（代码 AST 压缩）只在必要时动用。实测 case_1（RedisTimeoutException）短路触发，省去 L2 全部 token。

**护栏 G2：置信度分级 + 七节报告。** LLM 输出固定七节结构（① 根因链 ② 关键证据 ③ 定位置信度 ④ 修复建议 ⑤ 仍缺数据 ⑥ 排除的假设 ⑦ 一句话结论）；每条结论必须引用具体证据（日志行/代码行），置信度分 高（直接命中）/中（多处间接证据）/低（推断），**推断与有据结论显式分开标注** —— 这是反 LLM 幻觉的纪律性卡点。

**护栏 G3：errno 语义。** 遇到"返回空/空列表/空串"，先看 errno/statusCode —— errno=0 且空 = 业务事实空（用户确实无此数据，接口正常）；errno≠0 且空 = 接口/配置故障；禁止把"业务空"误判为"接口故障"（反之亦然）。

| 信号词扩展（not found/exit code/not supported） | LogDx-CI | 0.9082 → 0.9296 |
| 尾部保底 60→120 行 | LogDx-CI | 0.84 → 0.90 |
| 无损去重（集合一致性修复） | LogDx-CI | 0.76 → 0.9082（bug 修复） |

| BM25 弱信号裁剪（可选） | LogDx-CI | 压缩 94.94→95.28%（召回 0.9296 不变） |

### 4.5 稳定性

- LogDx-CI：确定性静态评分，零波动；
- re1ob 25 case × 3 轮：100%/100%/100%，零波动；
- RE3 re3ss 关键子集两次复现 25/30 一致。

## 5 讨论 (Discussion)

### 5.1 失败模式

**网络类故障（loss/delay）**：所有系统的失败集中在 loss/delay 故障（指标特征弱，官方 baseline 同样弱）。ours re1ob 的 7 个失败全部为 loss 故障。此类故障需网络层数据（丢包率/重传）或因果分析，超出日志/指标压缩范畴。

### 5.2 无追踪场景的竞品特例

RE3-ss（Sock Shop，无 traces）上 rtk 90.0% 高于 ours 83.3%。分析表明 rtk 的优势来自"信息最少化"：其输出仅 1198 chars（几乎无日志信息），LLM 被迫依赖指标信号（该数据集根因恰在指标中）。ours 的日志视图（20K chars）在此场景构成干扰。这是"日志噪声 vs 指标信号"的极端案例；当指标信号弱而日志信号强时（re1ss 等），ours 显著反超（96.8% vs rtk 在同类场景的劣势）。

### 5.3 局限

- 服务标签依赖日志格式（`[service]` 前缀），无服务标签的日志 SED 失效；
- 高价值过滤词表（LOW_VALUE_RE）面向 Java/HTTP 生态，其他技术栈需扩展；
- LLM 判分维度（自建 benchmark）有 ±7% 波动，需更多真实 case。

## 6 结论 (Conclusion)

本文提出 RootCause Agent：以信号工程为核心的 LLM 根因定位上下文压缩框架。在 565+ 个业界标准故障案例上与 7+ 开源方案和官方 baseline 的横向对比中，全部维度第一或并列第一，token 压缩率 94.5%–99.98%。关键洞见：**压缩的目标不是"尽可能小"，而是"把可靠信号以不误导的方式呈现给 LLM"**。我们开源全部代码与评测工程。
